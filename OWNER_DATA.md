# Публичные сведения продавца

При проверке брони используются `payments.getUniqueStarGift` и связанные с ответом пользователи/каналы. Если в ответе есть username, он отображается в личной карточке и кнопках профиля/оффера.

Если username отсутствует, проверяется исключительно ячейка Owner оригинальной публичной страницы `https://t.me/nft/<slug>`. При наличии прямой HTTPS-ссылки на публичный профиль t.me username сохраняется вместе с лотом до создания задания доставки. Чужие ссылки из остальных частей страницы не используются. Запрос ограничен 3 секундами и 256 КБ; ошибки сайта не отменяют бронь. Для кошельков этот способ не применяется: профиль, на котором размещён подарок, не обязательно является владельцем кошелька.

Если Telegram отдаёт только `owner_name`, показывается имя и «Username не раскрыт Telegram». Поиск аккаунта по совпадению имени не выполняется. Наличие username у продавцов из чужого трекера не означает, что Telegram раскрывает владельцев всех лотов.

Дополнительная проверка: если `owner_name` целиком записан как `@username`, выполняется `contacts.resolveUsername` и просмотр публичных подарков профиля через `payments.getSavedStarGifts` (до трёх страниц по 100). Контакт подтверждается только при наличии точного slug и ID подарка в этом профиле, без другого владельца и без признаков кошелька/хостинга. Одна надпись `@username` в имени сама по себе не считается доказательством. Скрытые подарки или подарок за пределами проверенных страниц этим способом не подтверждаются. FLOOD_WAIT и другие ошибки не отменяют бронь; попытки дополнительного поиска приостанавливаются.

Проверено 17 ноября 2026: публичная страница MirageLamp-112194 возвращала имя владельца без ссылки на аккаунт. Username этого продавца не установлен. Это ограничение доступных данных, а не доказательство отсутствия username у человека.

Документация: https://core.telegram.org/constructor/starGiftUnique и https://core.telegram.org/api/gifts

## Найденный внешний источник (17 ноября 2026)

У see.tg опубликован REST API https://kartoshka.free/ с собственной базой подарков, текущих владельцев и истории. Документированы `GET https://kartoshka.free/v1/gift/{ref}` и `GET /v1/owner/{ref}`. Авторизация — заголовок `Authorization: Bearer <токен приложения>`. Токен создаётся в мини-приложении see.tg → Полезное → API; для создания приложения требуется Telegram Premium.

Страница документации сообщает 100 запросов в сутки и 0.00005 TON за последующие, но это расходится с живым `GET /v1/pricing`: при проверке 17 ноября 2026 он вернул `freePerDay: 25`, `pricePerRequest: "0.002"`, `gift.who: "0.4"` TON. Ориентироваться нужно на текущий ответ тарифов, а не статичный рекламный текст. Без пополнения скорость 1 запрос/с; при исчерпании квоты и отсутствии баланса — 402. Сервис также имеет отдельный метод `/v1/gift/{ref}/who` с предположениями и разными уровнями доказательств; такой результат нельзя автоматически выдавать за достоверного текущего владельца. Во время расследования выполнены только неавторизованные `/v1/ping` (401) и `/v1/pricing` (200); платные запросы не выполнялись.

Это документированный кандидат для дополнения лотов, а не доказательство того, что @parserfexxabot использует именно его. Ключа API see.tg в проекте нет, авторизованный ответ по текущим подаркам не проверен. Реальный формат ответа и достоверность/свежесть сведений нужно проверить до написания маппера и включения источника. Нельзя обещать наличие username у всех подарков или выдавать исторического владельца за текущего.

## Проверка Fragment

17 ноября 2026 напрямую проверены публичные страницы `/gift/plushpepe-1821`, `/gift/plushpepe-1056`, `/gift/plushpepe-1515`, `/gift/plushpepe-1163`, взятые из текущего каталога https://fragment.com/gifts. Во всех четырёх ячейка Owner содержит TON-адрес и ссылку на блокчейн-обозреватель gram.org, без ссылки на Telegram-профиль. Это результат выборки, а не утверждение о каждой странице Fragment.

Запросы `/gift/libertyfigure-168936` и `/gift/miragelamp-112194` при проверке возвращали HTML главной страницы с HTTP 200, заголовком `Buy and Sell Usernames` и canonical `https://fragment.com/`. Встреченные на этой странице usernames относятся к аукционам имён, а не к владельцу запрошенного подарка. Код ответа 200 не доказывает наличие карточки; перед извлечением любых полей нужно проверять canonical и идентификатор предмета.

Официальный https://fragment.com/about поясняет, что площадка не хранит сведения, связывающие кошелёк с Telegram-аккаунтом. Наличие collectible username в том же кошельке не доказывает, что он назначен аккаунту владельца подарка. Универсальный способ получения текущего @username продавца внутреннего маркета через Fragment не подтверждён.

### Бесплатный путь, подтверждённый на живых данных

Скрипт `work/prove-free-profile-index.mjs` получил публичные подарки известного профиля `timmy_k` через `payments.getSavedStarGifts` с `excludeHosted=true`, `excludeUnsaved=true`. В ответе подарок `BigYear-27329` имел `ownerId`. Отдельный `payments.getUniqueStarGift` для того же slug не вернул `ownerId`, а вернул только `ownerName: "Тимур"`. Таким образом, профильный контекст действительно даёт сведения, которых нет в прямой карточке. Запросы только читали публичные данные, без покупок и сообщений продавцам.

Практическая бесплатная архитектура: известные публичные профили → периодические снимки их видимых подарков → локальный индекс точного slug/ID → повторное подтверждение владельца перед показом контакта. Нельзя считать старую запись индекса текущим владельцем после передачи. Скрытые, кошельковые и размещённые на чужом профиле подарки требуют отдельных проверок. Для неизвестных профилей начального индекса нет; наличие бесплатного универсального обратного поиска всех владельцев не доказано.

Постоянный индекс внедрён в версии `owner-index-v1`: миграция `002-owner-index.sql`, модуль `src/owner-index.js`, отдельный фоновый обработчик. При публикации создаётся сохраняемая задача подготовки контакта. Если профиль найден позже, контакт добавляется к свободному лоту в базе без редактирования группового сообщения. При бронировании индексный контакт повторно проверяется в публичных подарках профиля; старый снимок сам по себе не отправляется как подтверждённый контакт.

Стартовые публичные профили задаются `OWNER_PUBLIC_PROFILES` через запятую. Добавление без перезапуска: админ-панель → «Профили продавцов» → список @username. Явные @username из поля имени владельца новых опубликованных лотов также добавляются автоматически, но не считаются доказательством владения до проверки конкретного подарка. Новых запросов к платным сервисам нет.

Обход идёт по одной странице публичного профиля в фоне с паузой 5 секунд; завершённый профиль перепроверяется через 30 минут. FLOOD_WAIT сохраняется в базе и приостанавливает весь профильный обход. Скрытые подарки, несопоставленные ID, кошельки и чужие хостинги не индексируются. Сведения хранятся в базе и используются только для личной карточки; публичная карточка и её кнопки не получают username. Покрытие зависит от списка известных профилей, а не от общего числа объявлений.

После обновления файлов необходимо перезапустить процесс через restart-bot.bat. Уже отправленные личные сообщения автоматически не редактируются.

## Автоматическое расширение, owner-discovery-v2

Автосбор включён по умолчанию (`OWNER_AUTO_DISCOVERY=true`, `OWNER_MAX_PROFILES=5000`). Он получает кандидатов только из явно указанных Peer-ссылок публичных ответов Telegram: текущий владелец подарка, видимый отправитель сохранённого подарка, первоначальные отправитель и получатель из сохранённых OriginalDetails. Кандидат добавляется только если соответствующий пользователь/канал есть в том же ответе с публичным username. Нераскрытый отправитель, бот, удалённый/min/запрещённый профиль и не связанные с подарком участники ответа не используются. Имена и названия не превращаются в usernames путём догадки.

После добавления кандидат проходит обычную проверку публичных подарков. Указание человека как первоначального отправителя или получателя не делает его текущим владельцем: для контакта нужен точный подарок в его текущем публичном инвентаре с совпавшим ownerId. Источник обнаружения хранится в `owner_profile_sources`; подтверждённые снимки и изменения контактов — в `owner_observations`. Исторический владелец не подставляется вместо неизвестного текущего.

Профили обнаруживаются при обходе маркета, подробной проверке подарка и обходе уже известных профилей; новые профили автоматически попадают в очередь. Нет запросов к платным источникам, сообщений продавцам или чтения личных диалогов. Лимиты и паузы Telegram соблюдаются. Первоначальные стартовые публичные профили остаются нужны для начала обхода; существующая база подходит в качестве старта. Дальнейший рост зависит от наличия публичных связей и usernames, а не гарантирован для всех продавцов.

О see.tg удалось подтвердить по прямым публичным постам автора:
- https://t.me/seedottg/25 — автор описывает распределённый парсинг большого каталога с использованием множества аккаунтов;
- https://t.me/seedottg/69 — автор заявляет получение точных аккаунтов владельцев для части подарков после изменения Telegram, но не публикует технический алгоритм;
- открытый Seegram-клиент запрашивает дополнительные данные у авторизованного сервера see.tg. Серверный алгоритм получения скрытых владельцев в изученных материалах не раскрыт.

Реализация проекта — собственный бесплатный сбор публичных подтверждений, не доказанная копия внутреннего механизма see.tg и не обещание их покрытия.

### Гостевая лента объявлений see.tg

В документации see.tg описан WebSocket `wss://live.see.tg/v1/ws`: без токена он работает как guest и отдаёт те же типы событий без ID профилей и с частично скрытыми именами. Добавлен отдельный адаптер `src/see-source.js`: он слушает события `listing`, `price`, `delisting` только для рынка `telegram`, пишет события в SQLite, публикует новые листинги, редактирует карточку при изменении цены и убирает бронь при снятии. Документация: [kartoshka.free API](https://kartoshka.free/) → WebSocket.

Гостевой поток сам по себе не раскрывает username. Перед резервом событие сверяется по slug и цене через отдельную пользовательскую MTProto-сессию. Поток best-effort: он не гарантирует получение пропущенных событий во время отключения; see.tg может отключить отдельный тип. Мониторинг включён по умолчанию при `SOURCE=telegram`, выключается переменной `SEE_FEED_ENABLED=false`. Статус соединения и последнего события виден в `/admin stats`.

Добавлен необязательный `SEE_API_TOKEN`: если он настроен, адаптер проверяет свободную квоту через `/v1/me`, затем читает точную карточку по `/v1/gift/{slug}` и берёт username только из публичного текущего owner-профиля этого подарка. Платный `/who` не вызывается. Без токена или свободной квоты resolver пропускает запрос, поэтому для новых лотов username появится только после добавления токена. Приватные профили и простые совпадения имени не считаются доказательством.
